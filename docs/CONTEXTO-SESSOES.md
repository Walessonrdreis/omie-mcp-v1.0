# Contexto das Sessões

Log cronológico de cada sessão de trabalho relevante neste projeto: o que foi feito, decisões tomadas e o que ficou pendente. Mantido pela skill `memoria-sessao` (`.claude/skills/memoria-sessao/SKILL.md`).

Objetivo: qualquer nova conversa (ou pessoa) consegue ler as entradas mais recentes abaixo e entender rapidamente onde o trabalho parou, sem precisar reconstruir o contexto a partir do histórico de chat ou do git log.

Para o que foi implementado tecnicamente (não o que aconteceu em cada sessão), veja `docs/GERAL.md`.

## 2026-07-20 — Cobertura financeira, hardening de rate limit e infraestrutura de acesso

- **Autor/Interlocutor:** Walesson
- **O que foi feito:**
  - Estabelecida a arquitetura híbrida do MCP: módulos passthrough (`src/tools/*.ts`) para endpoints que a Omie já devolve prontos, e módulos em camadas (`src/modules/<nome>/`, clean architecture) quando há lógica de negócio (agregação, cruzamento, paginação).
  - Construídos módulos em camadas: `produtos` (estoque calculado por produto), `estoque` (total por produto somando locais), `ordemProducao` (OPs com produto resolvido), `pedidoVenda` (pedidos com cliente/itens, produtos para separar, atalho "Separar Estoque"), `clientesFornecedores` (cliente e fornecedor são o mesmo cadastro Omie, diferenciados por tag — renomeado de `clientes` a pedido do usuário), `contasCorrentes`, `fluxoCaixa` (relatório de fluxo de caixa que a Omie não tem pronto, com contas favoritas e opção de saldo real).
  - Hardening do `OmieClient`: throttle de 300ms entre chamadas, retry com espera baseada na mensagem de erro da Omie, `mapWithConcurrency` para limitar fan-out — corrigiu bugs reais de rate limit ("consumo indevido"/"consumo redundante") e a descoberta de que a Omie rejeita duas chamadas concorrentes do mesmo método.
  - Criado `src/httpServer.ts`: API REST local (só `127.0.0.1`, sem autenticação) reaproveitando a mesma lógica do MCP, com rotas de descoberta de schema (`/tools`, `/tools/:name/schema`) — passo intermediário rumo a um futuro frontend/backend próprio, sem expor o MCP remotamente ainda.
  - Adicionados os módulos `contasPagar` e `contasReceber` (listagem com nome do fornecedor/cliente resolvido), documentados em README.md e FUNCIONALIDADES.md, e implementado filtro de data (`data_alteracao_de`/`ate`) em ambos.
  - Criado `COMO_USAR.md` na raiz — guia de referência com todos os comandos `curl` e payloads de cada ferramenta, para consulta quando os tokens do Claude acabarem.
  - Promovidas as skills `documentacao-viva` e `memoria-sessao` de locais (`omie-mcp/.claude/skills/`) para globais (`~/.claude/skills/`), disponíveis em qualquer projeto novo.
- **Decisões tomadas:**
  - Escopo de clientes/fornecedores fica **só leitura** até o MCP ter segurança mínima implantada — CRUD completo fica para depois.
  - MCP não será exposto remotamente (Connector) até ter segurança mínima — a API HTTP local não muda essa decisão, só facilita consumo local.
  - O filtro nativo da Omie (`filtrar_por_data_de/ate`) em `financas/contapagar`/`financas/contareceber` filtra pela **data de última alteração do lançamento**, não pelo vencimento — confirmado testando a API. Por isso o MCP expõe o parâmetro como `data_alteracao_de/ate`, para não sugerir um comportamento que a API não tem.
- **Pendências / próximos passos:**
  - Gap-analysis pendente: mapear o que ainda falta cobrir da Omie (CRM, NF-e, Serviços/NFS-e, Painel do Contador nunca foram explorados; várias tools de finanças como extrato, boleto, pix, orçamentos ainda só via `omie_chamar_api` genérico).
  - Confirmar se as duas contas "iFood" cadastradas em `CONTAS_FAVORITAS` do fluxo de caixa são duplicidade real ou contas distintas legítimas.
  - Avaliar se remove as cópias locais das skills em `omie-mcp/.claude/skills/` agora que existem globais.
- **Docs relacionadas:** README.md (arquitetura, todos os módulos, rate limit), FUNCIONALIDADES.md, `COMO_USAR.md` (novo).

## 2026-07-20 — Segurança mínima na API HTTP local (autenticação por API key)

- **Autor/Interlocutor:** Walesson
- **O que foi feito:** implementada autenticação por API key estática no `httpServer.ts` — toda rota agora exige header `Authorization: Bearer <HTTP_API_KEY>`, validado com comparação timing-safe; o servidor recusa subir (`process.exit(1)`) se `HTTP_API_KEY` não estiver definida no `.env`. Criado `scripts/gerar-api-key.mjs` (`npm run gerar-api-key`) pra gerar a chave. Atualizados `.env.example`, `README.md` e `COMO_USAR.md` (todos os exemplos de `curl` agora incluem o header). Testado manualmente: 401 sem header/com chave errada, 200 com chave certa; servidor recusa iniciar sem `HTTP_API_KEY`.
  - **Atualizado em:** 2026-07-20 — adicionadas mais duas camadas: rate limit (janela fixa, 120 req/min, `429` acima disso) e confirmação obrigatória (`"confirmar": true` no payload) em ferramentas que incluem/alteram/excluem dado na Omie. Novo campo `destructive?: boolean` em `ToolDef` (`src/tools/types.ts`), marcado em `omie_op_incluir/alterar/excluir`, `omie_estoque_ajuste_incluir`, `omie_requisicao_compra_incluir`, `omie_pedido_compra_incluir`; `omie_chamar_api` detecta pelo prefixo do `call` (Incluir/Alterar/Excluir/Cancelar/Deletar). Testado manualmente: 400 sem confirmar, passa da checagem com confirmar, 429 a partir da 121ª requisição no minuto.
- **Decisões tomadas:** API key estática (não Basic Auth, não mTLS) é o mínimo suficiente pro estágio atual — uso local, single-user. Decisão tomada com o usuário via pergunta direta antes de implementar. Fica como base pra evoluir (ex: OAuth) se o servidor for exposto como Connector remoto no futuro — isso continua bloqueado por ora. Rate limit e confirmação foram escolhidos (entre as opções levantadas) como as camadas de maior retorno pro estágio atual — auditoria e chave por escopo (leitura/escrita) ficaram pra quando a escrita estiver em uso real.
- **Pendências / próximos passos:** com a autenticação mínima implantada, destravar os itens que dependiam dela: CRUD completo de clientes/fornecedores (hoje só leitura) e inclusão/consulta de contas a pagar/receber. MCP (stdio) em si não foi alterado — a lacuna de segurança era só na API HTTP.
- **Docs relacionadas:** [API](./API.md#autenticação-por-api-key-na-api-http-local-httpserverts), [API — rate limit e confirmação](./API.md#rate-limit-e-confirmação-obrigatória-em-operações-destrutivas-na-api-http-local), [Índice Geral](./GERAL.md)

## 2026-07-20 — Abstração de gateways da Omie com interfaces + fake gateways + testes (vitest)

- **Autor/Interlocutor:** Walesson
- **O que foi feito:** para os 9 módulos em camadas (`estoque`, `produtos`, `ordemProducao`, `pedidoVenda`, `clientesFornecedores`, `contasCorrentes`, `fluxoCaixa`, `contasPagar`, `contasReceber`), extraída uma interface (`domain/interfaces/<nome>-gateway.ts`) de cada gateway concreto, com o gateway real passando a `implements` essa interface; criado um gateway fake em memória (`infrastructure/gateways/<nome>-fake-gateway.ts`) para cada um; use cases passaram a depender das interfaces (não das classes concretas), inclusive nas dependências cruzadas entre módulos (ex: `pedidoVenda`/`contasPagar`/`contasReceber` dependem de `IClientesGateway`, `fluxoCaixa` depende de `IContasCorrentesGateway`); tools em `presentation/mcp/*-tools.ts` escolhem gateway real ou fake via `process.env.OMIE_MOCK === "true"` (padrão: real, sem essa env var); `index.ts` de cada módulo passou a exportar a interface e as duas implementações. Instalado `vitest` (`npm run test`), com testes de use case usando os fakes — 21 testes no total, cobrindo soma de estoque, cruzamento produto+estoque, enriquecimento de OP, resolução de cliente/etapa em pedidos, filtro de cancelados, dedup do fake de clientes, agregação de fluxo de caixa (realizado vs. previsto, exclusão de cancelado, saldo real a partir de saldo_inicial/saldo_data), e resolução de fornecedor/cliente em contas a pagar/receber (incluindo o caso de código não encontrado no cadastro). `tsconfig.json` passou a excluir `**/*.test.ts` do build de produção (achado ao rodar `npm run build` depois do primeiro teste — sem isso o `.test.js` ia parar no `dist/`). Validado manualmente fim a fim via `httpServer.ts` com `OMIE_MOCK=true` em todos os 9 módulos.
- **Decisões tomadas:** piloto começou por `estoque` (módulo mais simples) pra validar o padrão antes de replicar; ordem dos módulos seguintes decidida um a um pelo usuário a cada resposta, não em lote. Quando um gateway concreto é reaproveitado por outro módulo (ex: `EstoqueOmieGateway` usado por `produtos`), o tipo de retorno (`ProdutoOmie`, `PosicaoEstoque` etc.) é re-exportado do arquivo do gateway concreto para não quebrar imports existentes entre módulos. `clientesFornecedores` e `contasCorrentes` ganharam interface/fake como pré-requisito de outros módulos (`pedidoVenda` e `fluxoCaixa`, respectivamente) antes de serem pedidos explicitamente — as tools desses dois módulos são passthrough/chamam `client` direto, então não precisaram de mudança, só o teste do fake. Registrada a convenção em `docs/PADRAO-PROJETO.md` agora que está completa nos 9 módulos.
- **Pendências / próximos passos:** nenhuma — os 9 módulos estão no padrão, build e suíte de testes (21/21) passando.
- **Docs relacionadas:** [Padrão de Projeto — gateway abstraído](./PADRAO-PROJETO.md#gateway-abstraído-por-interface--fake-gateway--omie_mock), [Índice Geral](./GERAL.md).

## 2026-07-20 — Módulo de estrutura de produtos (BOM/ficha técnica) com busca por nome

- **Autor/Interlocutor:** Walesson
- **O que foi feito:** identificada a lacuna "o MCP não sabia buscar a estrutura de um produto pelo nome" (ex: "estrutura do produto 100kg" exigia já saber o código Omie). Investigado ao vivo contra a API real: `ConsultarEstrutura` estava com o resource errado (`produtos/malha`, correto é `geral/malha`); confirmado que o método `ListarEstruturas` (mesmo resource) existe e já devolve nome do produto e de cada insumo prontos (não precisa cruzar com o cadastro de produtos). Criado o módulo `src/modules/estrutura/` (padrão camadas: gateway+interface+fake+teste) com duas ferramentas: `omie_estrutura_listar` (todos os produtos com ficha técnica) e `omie_estrutura_buscar_por_produto` (acha pela descrição/trecho dela ou código, paginando client-side já que a API não tem busca por texto nesse endpoint). Removido o antigo `omie_estrutura_consultar` (passthrough com resource errado) do módulo `ordemProducao`. Validado fim a fim contra a conta Omie real (produto "100kg", código `9116171995`/`100kg`) e via `npm run build` + `npx vitest run` (26/26 passando).
- **Decisões tomadas:** a busca por nome pagina a listagem inteira (597 registros / 120 páginas nessa conta) em vez de tentar um filtro server-side, porque `ListarEstruturas` não aceita filtro de texto (só paginação) — se o volume crescer muito e isso incomodar, cachear é o próximo passo natural, não reescrever a busca.
- **Pendências / próximos passos:** ~~a ferramenta nova só fica disponível depois que a conexão MCP for reiniciada~~ — segue valendo pra todo o módulo depois da atualização abaixo.
- **Docs relacionadas:** README.md (seção "Estrutura de Produtos"), FUNCIONALIDADES.md.
- **Atualizado em 2026-07-20:** completado o CRUD do módulo, já seguindo o padrão gateway+interface+fake+teste desde o início (aprendido do ciclo de `produtos` logo acima). `IEstruturaGateway` ganhou `incluirItensEstrutura`/`alterarItensEstrutura`/`excluirItemEstrutura`; implementado em `EstruturaOmieGateway` e `EstruturaFakeGateway` (que também teve o bug do array `ESTRUTURAS_FAKE` compartilhado por referência corrigido, mesmo caso do `ProdutosFakeGateway`). Validado ao vivo com round-trip completo e seguro: criados 2 produtos de teste descartáveis (pai tipo '04 - Produto Acabado' + insumo), `IncluirEstrutura` → `AlterarEstrutura` → `ExcluirEstrutura` no item, depois os 2 produtos de teste excluídos — nenhum rastro ficou na conta. Achados reais que corrigem a doc pública da Omie: (1) o produto pai só aceita `IncluirEstrutura` se `tipoItem` for '03 - Produto em Processo' ou '04 - Produto Acabado'; (2) `intMalha` é obrigatório no item de `IncluirEstrutura`, apesar de listado como opcional; (3) `AlterarEstrutura` exige `idProdMalha` junto do `idMalha` mesmo só pra mudar quantidade. Corrigido também um bug preexistente nos dados fake (`ESTRUTURAS_FAKE`): os dois itens do produto 111 tinham `idMalha: 1` duplicado — pego pelo teste de exclusão, que falhava porque o `some()` ainda achava idMalha 1 depois de remover só o primeiro. Novos testes em `estrutura-crud.test.ts` (5 casos) — suíte total 37/37.

## 2026-07-20 — CRUD completo de Produtos (Incluir/Alterar/Excluir)

- **Autor/Interlocutor:** Walesson
- **O que foi feito:** pesquisado o catálogo completo de endpoints "produto" da Omie (developer.omie.com.br/service-list) e comparado com o que já existia no código — antes só havia Consultar/Listar. Primeira versão foi implementada como passthrough direto (`resource`+`call`, sem gateway); validada ao vivo com round-trip seguro (criar → alterar → excluir o mesmo produto de teste, sem deixar rastro) — achado real: `IncluirProduto` exige `codigo` (SKU) como obrigatório, embora a doc pública da Omie marque como opcional. **Refeito a pedido do usuário** pra seguir o padrão já consolidado do projeto (gateway abstraído por interface + fake gateway + teste, ver `docs/PADRAO-PROJETO.md`): `IProdutosGateway` ganhou `incluirProduto`/`alterarProduto`/`excluirProduto`; `ProdutosOmieGateway` implementa contra a Omie real; `ProdutosFakeGateway` passou a de fato criar/alterar/excluir em memória (e seu construtor foi corrigido pra não compartilhar mais o array `PRODUTOS_FAKE` por referência entre instâncias — antes era só leitura e isso não importava, agora mutação vazaria estado entre testes); criados use-cases finos (`IncluirProdutoUseCase`/`AlterarProdutoUseCase`/`ExcluirProdutoUseCase`) e DTOs Zod (`produto-crud.dto.ts`); as tools MCP passaram a chamar os use-cases em vez do passthrough. Adicionados 6 testes novos (`produto-crud.test.ts`) cobrindo incluir, duplicata recusada, alterar por código, alterar inexistente falha, excluir, e isolamento de estado entre instâncias do fake — tudo sem tocar na Omie real.
- **Decisões tomadas:** a validação ao vivo contra a API real (round-trip) foi mantida como o que descobriu o comportamento verdadeiro da API (campo `codigo` obrigatório) — o padrão gateway+fake resolve *testar depois*, não substitui a necessidade de validar contra a API real pelo menos uma vez ao implementar algo novo. Ficou de fora deste ciclo o restante do catálogo de "produto" mapeado na pesquisa anterior (características, kit, variação, lote, unidade de medida, tabela de preços, NCM, produto-fornecedor, comprador, locais/resumo de estoque) — implementar só o que o usuário pedir, não antecipar.
- **Pendências / próximos passos:** as ferramentas novas só ficam disponíveis depois que a conexão MCP for reiniciada (mesmo caso do módulo `estrutura` desta mesma sessão).
